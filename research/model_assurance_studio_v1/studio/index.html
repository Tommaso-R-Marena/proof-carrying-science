02 / Assurance policy

Choose bounded, transparent checks. These thresholds create specific claims—not a universal safety verdict.

Under the assumption that all input values lie in this range, check whether model outputs remain in the required range. Supports a deliberately restricted scalar subset and tiny FLOAT32 dense neural networks (MatMul/Gemm/Add/Relu/Identity).

To compare two ONNX files, add the original first and updated second, then choose Compare selected ONNX model pair. The original bound is the relational output upper bound above. The same per-feature input box and coefficients apply to both versions.

Example: coefficients -1,1 and limit -1/4 prove output 0 beats output 1 by at least 0.25 for all inputs in the assumed box. Reviewer must obtain and pin their desired policy independently. The IEEE binary32 check uses a separate explicitly specified sequential operation order. Neither its result nor an exact-real proof establishes deployed ONNX Runtime or Lean verification.

For tightly screened float32 operators and embedded weights only. No execution of uploaded code, official ONNX Runtime in this local interface, external weight files, or secure sandbox. Real ONNX Runtime checks require an optional local CLI and trusted inputs.

What each verdict means

PASS — A particular static check held.
FAIL — A specific check was violated or parsing rejected.
OPEN — Insufficient evidence, unsupported format, or additional validation required.

03 / Evidence and findings

Your analyses will appear here, with each model's checks, limitations and downloadable receipt.
Explicit assurance boundary: This prototype performs strict screened ONNX parsing, static inspection, bounded exact rational mathematical checks, optional screened float32 scalar/dense-network replay and synthetic tool-use policy inspection or guarded in-memory execution. NumPy/PyTorch replay, MILP search, and finite-cover certificates do not establish an isolated security sandbox or official ONNX Runtime equivalence. Reports are SHA-256-bound unsigned research receipts by default; optional separately pinned Ed25519 publisher signatures are available via CLI, never Lean-kernel certificates, formal PCS v0.6 packages, regulatory approvals, biological validation, or demonstrations of model alignment. No cloud service is contacted by the local interface. Exact relational certificates use idealized real arithmetic. Binary32 analysis uses exact rational bounds under an explicitly stated model of rounded operations, not verified universal ONNX Runtime semantics. The LP-dual checker does not use a trusted optimizer. The optional v0.10 dual-proof demo requires both a full exact-real/update proof family and a direct binary32 partition cover; the operating-envelope demo admits only input regions with a complete set of verified conditional class-margin certificates; this is not a secure deployment boundary or actual ONNX Runtime execution.
