# What the Lean model and the ClaimCheck code have in common, and how we know

Status 2026-11-17, on top of `fe76d25b`. Everything here can be re-run with the commands at the end.

Four kinds of statement are kept apart:

* **Proved**: a theorem checked by the Lean 4.28.0 kernel about Lean definitions. The axiom report
  (`formal/AXIOMS.expected`, 67 lines) names only `propext`, `Classical.choice` and `Quot.sound`.
  A theorem about a Lean definition says nothing about the Python or C code by itself.
* **Exhaustively checked on a finite abstraction**: every point of a finite input domain of a Lean
  function is evaluated by Lean and compared with the Python code driven at that point. This is
  evidence about the code on that abstraction, not a proof about Python: the interpreter, the
  stubs, and the mapping from Python data to the abstract points are trusted.
* **Sample-tested**: a finite set of vectors with no completeness claim.
* **Trusted**: assumed here, not checked.

Thousands of agreeing vectors are not a proof of equivalence. No statement below says otherwise.

## (a) Claims grammar: the generated part of a proof file

| | |
|---|---|
| Proved (`ClaimCheckAssurance/Claims.lean`) | `parseTail_iff`: the Lean parser accepts `t` with result `(d, cs, os)` exactly when the values are valid and `t = renderTail d cs os`. `renderTail_injective` and `same_meaning_same_text`: different valid values never share a text, and two accepted texts with the same data and the same denoted claims and outcomes are the same text. `batch_iff_claims`: the batch theorem holds exactly when every per-claim theorem holds. `parseTail_header` and `parseTail_source`: an accepted tail starts with the canonical header of `d`, whose numerals denote a well-formed `Source` with bytes exactly `d`. |
| Sample-tested (`test_claims_refinement.py`) | The installed runner's `parse_tail` (Python, `claimcheck_v1_1/claimcheck_kernel_runner.py`) against the proved Lean `parseTail`, executed with `lean --run` rather than re-implemented. **10,720 vectors, 0 disagreements** (`claims_refinement_result.json`): all 84 committed obligation files; 400 generated by `batch_tail`; 1,389 non-canonical spellings; 3,209 truncations; 1,800 character mutations; 360 byte-level vectors; 6 forgeries; 3,424 token-level mutations (each token deleted, doubled or replaced by a near miss); 36 boundary vectors both must accept and 12 both must refuse. The boundaries are 65,536 vs 65,537 data bytes; 256 vs 257 claims; byte lists `[0, 127, 128, 255]` accepted and `[256]`, `[007]`, `[]` and lists of safe characters refused; empty, all-safe-character and 5,000-character strings; every statistic, including `.share` with nested filters; all six comparisons; rationals that are zero, negative or have 40- to 50-digit parts; square roots with sign −1, 0 and 1 and radicands 0, 1/3 and 10^40/7; all nine undefined reasons. | Trusted | The Python regular-expression engine and the runner code; the Lean interpreter that runs the comparison (the theorems are kernel-checked, but the comparison executes the definition). |

## (c) Authority policy: the outward verdict

**Proved** (`Authority.lean`, about the model): a CONFIRMATION needs a kernel-accepted match with
every match gate passed, or a confirmed sibling (`core_confirmation`, `confirmation_sound`). A
DISCREPANCY_FOR_REVIEW needs a kernel-accepted mismatch with every mismatch gate and a confirmed
same-column sibling (`core_discrepancy`, `discrepancy_corroborated`, `discrepancy_sound`). Two
statuses are always UNKNOWN: not established and undefined (`outward_unknown`,
`verdict_unknown_of_unaccepted`). A conditional result is never decided
(`conditional_never_decided`). Notes are ignored (`verdict_ignores_notes`). Withdrawing evidence
never upgrades a verdict (`verdict_mono`, `decided_of_withdrawn`). No number is both confirmed and
flagged (`no_conflict`). All of this holds under the stated input conditions (`KernelSound`,
`Doc.WellFormed`, `EnumerationConsistent`) and for arbitrary findings and sibling relations, which
come from untrusted code. The theorems quantify over the variants a record carries. The model does
not say that those are the variants the reading requires; part (d) shows why that matters.

**Exhaustively checked on finite abstractions** (`check_conformance.py`, `conformance_report.json`):

| part | Lean function and finite domain | Python driven | result |
|---|---|---|---|
| B | `core`: 5 statuses × 2^5 aggregated facts = 160 states | `_decide`, every decomposition of each state | 2,560 calls agree |
| C | `outward` on two slices: mismatch gates (512) and match gates (64) | `_decide`, `_numeric_evidence` | 384 + 64 agree; 128 mismatch states have no Python input |
| D (new) | `mathStatus`: all 84 patterns of 1–3 variants, each a match, a mismatch, an undefined statistic or not accepted | the real `pipeline._complete`, then `policy.math_status` | **24,696 receipts agree**: every concrete form of each kind (rational or square-root value; two undefined reasons; for a variant the kernel did not accept, each of three predictions with no Lean record or with a refusal); binding gate passed or failed; conventions named or not |
| E (new) | `outward m f corM corD` on its **whole** domain: 5 × 2^16 × 2 × 2 = **1,310,720 points**, printed by Lean at test time (`ExportOutward.lean`, about 5.5 s, table SHA-256 `0b3cad32…7ee76c83`) | `_numeric_evidence` for a decided match (as `assess_document` does), then `_decide` | **983,040 points agree** (CONFIRMATION 2,112; DISCREPANCY 32; REVIEW 145,312; UNKNOWN 835,584; Python about 14 s). The other **327,680** have no Python input: a count whose dispersion wording fails, which no input produces because a count is not a dispersion statistic |

Before this change, the comparison covered all 160 `core` states, but only 448 of the 1,310,720
`outward` points (the two slices of C) and 6 of the 84 `mathStatus` patterns (through committed
receipts). It did not cover the whole finite domain; D and E now do.

In E, the facts the code computes from the receipt, the sentence and the predicted values are
computed by the real code from a constructed input. These facts are the status, not-a-count,
rounding, dispersion wording, out-of-grammar wording and the printed sample size. The other
findings come from stubs, and so does the sibling relation. On the 24,576 points that reach the
match or the mismatch rules, every finding the code reports is checked against the abstract fact it
stands for, and the mismatch rules must report all of theirs. Each abstract point gets one concrete
input. Where several inputs fit (for example which out-of-grammar word, or which way the quote
check fails), a seeded generator picks among 52 alternatives, and each alternative is used. For
393,216 of the checked points, the receipt is one that v1 never writes: a decided result without a
decided status, or with failed quote checks. They agree too.

**Sample-tested**: part A runs the 302 receipts of the six held-out bundles through the real
`assess_document`, with real helpers and real siblings. They reach 6 core states and 6 variant
patterns.

**Not covered, or trusted**:

* **How findings are computed** (reading-space enumeration, positional wording, units): this is
  stubbed in B, C and E. By design the model takes findings as untrusted inputs, so this is not a
  gap in the theorems. It does mean the correctness of findings is outside the formal argument and
  rests on evaluation.
* **Composition across receipts**: which receipts are strong matches and which are siblings
  (`assess_document`'s `strong` list and `corroborators`). E takes `corM` and `corD` as inputs, and
  only part A tests the composition. (The model allows sibling relations the code cannot produce,
  for example `corD` without `corM`; that over-approximation is safe for the theorems.)
* **Input condition of E.** `_decide` chooses the match or the mismatch rules by
  `receipt["result"]`; the model chooses by the mathematical status. The two coincide on every
  receipt v1 writes: D checks `_complete`, and both replayers recompute the result from the status
  and refuse a mismatch (`test_binding_offline`). `_decide` itself does not check this. A receipt
  edited to have status MATCH_PROVED with result REFUTED gets DISCREPANCY_FOR_REVIEW, and one with
  MISMATCH_PROVED and result PROVED gets CONFIRMATION. Both are recorded, not asserted, in
  `conformance_report.json`. `verify` builds receipts in-process, and `export_site_v11` reads
  committed receipts. The cheapest closure is one guard in `_decide` that requires the result to
  match the status; that is the owner's decision, and `policy.py` is not changed here.
* Python semantics, and the mapping of receipt and `Item` fields to the model's Booleans. Part E
  constructs that mapping and checks it by assertion.

## (d) Binding across runner, receipt and replay

**Proved**: (a) and (b) above. An accepted generated part's numeral denotes exactly its data bytes,
and its batch theorem is equivalent to its per-claim theorems. `KernelSound` stands for the
assumption that the kernel is sound and that the file's text denotes the equation it states.

**Tested before this change**:

* `tests/test_runner_strict.py`, offline: every committed obligation file is canonical; the reported
  forgery and every negative control are refused before Lean starts; size limits; only the
  generator's spelling is accepted.
* `runner/test_strict_tail.py`: the same, plus the withdrawn runner's defect reproduced with the
  real kernel.
* `check_live_v11.runner_cases`, with the real kernel: a genuine file is accepted and `data_sha256`
  equals the data's digest; a forged outcome is rejected by Lean; a shadowed `run` is refused
  before Lean.
* `check_live_v11.tamper_cases`, with the real kernel, all seven resealed: verdict upgraded,
  findings edited, data substituted, checker edited, kernel outcome forged, corroboration removed,
  records from another bundle.
* `claimcheck_v1/tests` ReplayTests, offline: edits that are not resealed.

**Added** (`claimcheck_v1_1/tests/test_binding_offline.py`: 15 offline tests, about 5 s). Every
forgery is resealed, so a check of meaning has to refuse it, not a stale digest:

* (a) Receipts about other data presented with this data file are refused (the receipt names
  different data bytes, and the obligation differs from the one re-derived).
* (b) An edited data digest is refused (re-derivation). Substituted data with re-derived
  obligations, and an edited outcome with a re-derived obligation, are refused offline only by the
  second calculation. The kernel rejects both too: this was run by hand with Lean 4.28.0, and
  `check_live_v11`'s outcome forgery does not re-derive the obligation, so there the comparison
  refuses it before Lean. A result whose polarity contradicts the kernel's status is refused, which
  is the input condition of part E in (c).
* (c) Records of another bundle about the same data are refused. Two genuine proof files about the
  same data, with different claims and identical outcomes, give kernel-run receipts with the same
  data digest and the same proved outcomes. Only the proof file's digest (and its size and name)
  tells them apart.
* (d) A canonical obligation that embeds other data, with its digests updated in the receipts, is
  refused.
* (e) Each of 31 malformed bundles (truncated or mistyped JSON, missing keys, nulls, non-UTF-8
  files, missing files, out-of-range indices) fails closed: non-zero exit, and never `all_replayed`.
* (f) A conditional record relabelled MATCH_PROVED is refused, and so is a conditional receipt
  relabelled PROVED.

**Finding (2026-11-17): three forgeries pass the independent replay, including the kernel
re-check.** All three are resealed bundles, and all were replayed with Lean 4.28.0 re-checking both
obligation files; the result was `all_replayed: true`:

1. **Dropped convention.** An SD reading whose n − 1 convention matches and whose n convention does
   not (CONDITIONAL_ON_CONVENTION) loses its n variant. It becomes MATCH_PROVED.
2. **Another statistic.** A mean that does not match (printed 14.26; the file's mean is 14.76) gets a
   variant whose `stat` is `median`. The file's median is 14.26, so the reading becomes MATCH_PROVED,
   while the receipt still reads "The arithmetic mean of mass …".
3. **Another reported value.** The sentence prints 111.2, and `q2` still records 111.2 at its
   offsets. The claim's `reported` is edited to 109.5, the file's mean, and the reading becomes
   MATCH_PROVED.

With fabricated findings, which the replay takes as recorded and says so, each of the three becomes
a CONFIRMATION. The cause is that both replayers check that each obligation is the one rendered from
the receipt's claim, the variant's `stat` and the predicted outcome, and that the quote and the
number sit at the recorded offsets. They do not check that the claim is the sentence's:

* the claim's `reported` is never compared with the printed literal;
* a variant's statistic is never compared with the reading;
* the set of variants is never re-derived.

The kernel cannot catch this, because the theorem that remains is true; it is about another
statement. No theorem of (c) is contradicted either: they quantify over the variants a record
carries, and the binding of those variants to the reading is not modelled. The gap matters for
bundles handed to a reviewer, which is exactly what the replay is for. It does not arise in
`verify`, which builds receipts itself.

The cheapest closure needs owner approval, because the replayers are evidence tools; they are not
changed here. In both replayers:

* require `claim.spec.reported == q2.reported_value.literal_checked`;
* require the variants' `(stat, assumption)` to equal the expansion of `spec.stat` under the
  manifest: the SD family gives n − 1 and n unless the manifest declares one; every other statistic
  gives itself.

On all 302 committed receipts both conditions already hold: `literal_checked == reported` on all
262 that have a printed number, and the variants equal `pipeline.expand_spec` on every receipt.
Tests `test_known_gap_*` pin the three forgeries. They assert that the replay accepts them, so they
fail, with a message, once the replayers are corrected.

**Further limits of the binding, by design or not yet addressed**:

* A kernel-run receipt does not restate the claims. It is bound to them only through
  `proof_file_sha256`, so a consumer must compare that digest with the file it generated.
* A kernel-run receipt is not signed. It is a report; the evidence is running the kernel again.
* The manifest, including its data pin and any declared SD convention, is a submitter input. The
  replay cannot check it against anything outside the bundle.
* Findings that rest on the reading-space enumeration are taken as recorded by the replay, which
  says so in its output.

## Remaining gaps, cheapest credible closure, and whether to do it now

| gap | cheapest credible closure | now? |
|---|---|---|
| Replay does not bind the claim to the sentence (finding above) | The two checks above, about 20 lines in each replayer, then turn the `test_known_gap_*` tests into refusal tests | **Yes.** Concrete, cheap, high value; needs owner approval |
| `_decide` does not enforce the input condition of part E | One guard: a decided result must have the polarity of the status | Yes, together with the replay fix |
| Python parser ↔ proved Lean parser (tested, not proved) | Translation validation per proof file: have Lean run the proved `parseTail` on the file's generated part and require the runner's extraction to equal it, or kernel-check `parseTail t = some (…)` by `decide` (cost on 130 KB tails unmeasured) | Not now. 0 disagreements on 10,720 vectors, and the known forgery class is closed; the marginal gain is small |
| Composition across receipts (strong list, siblings) | An exhaustive two-record check against a Lean export of `Doc.verdict` (a few thousand cases) | Cheap. Worth doing before the policy is frozen for a prospective run, after the two items above |
| How findings are computed | Outside the formal argument by design | No formal work. This is what development and prospective evaluation measure; scientific validation matters more here |

Overall: more formal work now has diminishing returns. The concrete credibility risks are the
binding between the claim and the sentence in the replay, which is fixable, and the scientific
validity of readings, which only evaluation can address. The recommendation is to fix the two
items marked yes, then put effort into integration and scientific validation.
